# Curio Clerk agent guide

Read this file before changing the project.

## Product invariants

- Unity version is pinned to `6000.3.21f1`.
- Android is portrait, API 29 minimum, API 36 target, ARM64, IL2CPP, AAB.
- The game remains fully playable offline without an account, telemetry consent, or an available ad.
- Only opt-in rewarded ads are allowed. No banner, interstitial, app-open ad, energy system, loot box, or forced timer.
- English and Korean are release languages. Any player-facing copy must be supplied in both languages.

## Architecture

- `Assets/Scripts/Core`: deterministic C# domain logic; no UnityEngine reference.
- `Assets/Scripts/Runtime/Content`: catalog and ScriptableObject definitions.
- `Assets/Scripts/Runtime/Infrastructure`: replaceable save, ads, analytics, privacy, time, and crash-reporting boundaries.
- `Assets/Scripts/Runtime/Presentation`: application states and uGUI/TMP presentation.
- `Assets/Scripts/Editor`: deterministic asset/scene generation, validation, and Android build automation.
- `Assets/Resources/Content` and `Assets/Scenes` are generated by `ProjectBuilder.BuildAll`. Change the source catalog or builder instead of hand-editing generated output.

## Workflow

For gameplay, narrative, UI and playtest work, read [Docs/QualityReview.md](Docs/QualityReview.md) before implementation. Review and improve fun (curiosity, deduction, experimentation, pacing and payoff) and polish (physical feedback, audiovisual continuity, language and presentation) as well as usability and reliability. During each broad game-quality cycle, evaluate opportunities in both fun and polish, choose the most valuable supported improvement within the user's authorized scope, implement it and compare the result; do not stop at a defect checklist or leave design hypotheses indefinitely untested. Proactively find and fix reproducible issues; do not wait for the user to enumerate defects or decide routine design details. Avoid changes without a concrete benefit. Test counts and a source-aware playthrough alone do not establish game quality. Keep unresolved findings, improvement hypotheses, evidence and next acceptance checks in that document. These instructions apply during authorized work; they do not start or authorize scheduled background runs.

1. Write a failing EditMode or PlayMode test for behavior changes.
2. Make the smallest implementation that passes it.
3. Run `scripts/test-unity.ps1` for in-scope validation and diagnose its output.
4. Run `ProjectBuilder.BuildAll` after content, localization, scene, font, icon, or player-setting changes.
5. Run `scripts/build-android.ps1` before a release handoff only when the requested scope includes an Android build.

The human developer authorizes AI agents to run the repository's Unity test and build scripts, launch or control Unity Editor/Hub, run `ProjectBuilder.BuildAll`, perform Android builds, and exercise the game for validation. Before using Unity's official MCP under the then-current Unity terms, update `Docs/MCPSetup.md` and start with read-only hierarchy, Console, and build-setting checks. Do not use a community Unity MCP. Confirm the exact project/worktree before any Unity action, preserve unrelated dirty files, record validation evidence, and keep scene or generated-asset writes within the approved task scope.

Before adding or changing art, audio, store media, generated text, or third-party assets, update `Docs/AIAssetProvenance.md` and `Docs/ThirdPartyNotices.md`. Never commit service credentials, real ad identifiers, purchase receipts, or tester personal data to a public branch.
