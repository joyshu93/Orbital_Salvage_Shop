# Curio Clerk 자율 품질 점검 / Autonomous quality review

목표는 사용자가 결함을 하나씩 찾아 지시해야 하는 상황을 줄이고, 스스로 추리하고 물건을 변화시키며 다음 사연을 알고 싶어지는 게임으로 발전시키는 것이다. 에이전트는 승인된 게임 작업 안에서 재미·완성도·사용성·안정성을 함께 평가하고, 효과가 클 개선을 직접 선택해 구현한 뒤 결과를 비교한다. 이 문서는 실행 중인 작업의 개발 규칙이며 예약 작업이나 상시 실행 서비스를 설치하지 않는다.

## 한 사이클의 실행

1. **기준 확인:** 현재 프로젝트·브랜치·커밋·dirty 파일과 실행할 APK의 소스를 확인한다. 최신 QA와 아래 미해결 항목을 읽는다. 예전 후보의 문제는 현재 버전에서 다시 확인하기 전까지 역사적 증거로 표시한다.
2. **화면부터 보기:** 가능하면 소스·정답·기존 풀이를 전달하지 않은 별도 검토자에게 현재 화면이나 짧은 플레이 기록을 준다. 검토자는 현재 목표, 눌러볼 곳, 예상 결과와 더 알아보고 싶은 질문을 먼저 기록한다. 이미 정답을 아는 에이전트라면 그 사실을 명시한다. 스크린샷 검토를 실제 입력이나 사람의 첫 플레이로 표현하지 않는다.
3. **실제 입력과 사건 흐름 확인:** 선택한 장면을 전용 QA 환경에서 진행한다. 행동마다 알아낸 사실, 가능한 추론, 시도와 새 결과를 기록하고 앞뒤 장면과 결말까지 연결해 본다. 합리적으로 보이는 오답, 관찰 생략, 도구가 선택된 상태에서 힌트 사용, 재시작·메뉴 왕복도 필요한 범위에서 시도한다. 같은 실패를 반복해도 새 정보가 없거나 화면에 없는 사실을 알아야 진행된다면 문제로 기록한다. 별도로 추론 없이 안내만 따라가는 구간, 변화 없는 반복, 준비 없이 나오는 발견·결말을 개선 후보로 찾는다.
4. **우선순위 선택:** 진행 불가·저장 손실을 먼저 처리한다. 그 뒤에는 플레이에 미치는 영향, 근거의 확실성, 수정 비용으로 결함과 재미·완성도 개선을 함께 비교한다. 핵심 행동의 반복감이나 발견의 보상 부족을 사소한 문구 정리 뒤로 자동 배치하지 않는다. 매 게임 품질 개선 사이클에서 아래 재미와 완성도 항목을 각각 평가하고, 가장 효과가 클 근거 있는 개선을 선정한다. 확인되지 않은 것은 가설로 표시하되, 현재 범위에서 작은 수정으로 검증할 수 있다면 구현·비교까지 진행한다. 가설이라는 이유로 사용자 제보를 기다리지 않는다. 특정 개수의 기능·분기·연출을 채우기 위한 변경은 하지 않는다.
5. **수정과 검증:** 변경 전에 어느 장면의 어떤 경험을 어떻게 바꿀지, 무엇을 비교할지 기록한다. 행동 변경은 재현 테스트를 먼저 실패시킨 뒤 고친다. 문구·그림·음향 변경은 출처 문서를 먼저 갱신한다. 수정자가 아닌 검토자가 가능한 범위에서 결과를 다시 확인한다. 관련 Editor 검사와 원래 문제가 나타난 실제 입력·화면을 통과해야 결함을 해결로 표시한다. 재미·완성도 개선은 같은 장면의 전후를 비교해 추론할 정보, 선택의 이유, 새로 드러나는 변화, 전개와 보상, 표현의 일관성이 의도대로 바뀌었는지 기록한다. 근거가 약해지거나 새 혼란·늘어진 흐름을 만들면 추가 수정하거나 그 변경만 되돌린다.
6. **통합과 인계:** 요청 범위의 검증을 마친 뒤 소스·QA·문제 및 개선 목록을 함께 갱신한다. 무엇을 고쳤는지와 무엇을 더 흥미롭거나 완성도 있게 만들었는지를 구분해 근거를 남긴다. 이미 확인된 큰 문제를 남겨둔 채 효과가 작은 작업으로 넘기지 않는다. 범위 안의 다음 중요한 결함·개선이 있으면 이어서 처리한다. 개선할 근거가 없거나 범위를 벗어나거나 외부 조건으로 확인할 수 없으면 그 근거와 다음 확인 조건을 남긴다.

각 항목은 개발자가 자율적으로 설계·개선할 대상이다. 아래 비교 근거는 설계 의도가 구현됐는지 확인하는 방법이며, 사람의 재미를 자동 점수로 판정하는 기준이 아니다.

|---|---|---|

| 추리와 발견 | 관찰한 성질·흔적을 연결해 도구나 다음 행동을 생각할 여지를 준다. 관찰문을 명령문으로 바꾸거나 정답을 숨기기만 해서 난도를 만들지 않는다. | 힌트 없이 보이는 단서 → 추론 가능한 이유 → 실험 → 확인된 사실을 기록한다. 단순 안내 복창 구간을 고치되 필요한 정보가 실제 화면에 남는지 확인한다. |
| 실험과 선택의 의미 | 왜 그 도구를 그 부분에 쓰는지 물리적 이유가 있고, 합리적인 다른 시도도 상태·위험에 관한 정보를 준다. 분기 수를 늘리기보다 플레이어의 판단이 필요한 행동을 만든다. | 서로 다른 시도의 예상과 실제 반응을 비교한다. 설명 없는 정답 조합 찾기, 의미 없는 추가 탭, 비용 없는 오답의 단조로운 응답을 확인한다. |

| 성취감과 감정적 보상 | 수리와 발견이 인물의 반응과 사건의 의미를 바꾼다. 첫 사건은 냉기 문제를 마무리하면서 우산의 목소리로 이어지고, Remembering Rain은 소연의 편지와 답장을 준비된 결말로 회수하는지 본다. | 초반의 부탁·단서가 어느 행동과 결말에서 돌아오는지 확인한다. 마지막 내레이션만으로 해결을 선언하지 않고 결과가 그림·인물·보관소에 어떻게 남는지 비교한다. |

기술 검사 통과, 에이전트의 화면 판단, 소스를 아는 완주, 사람의 자연 플레이는 각각 구분한다. 여러 에이전트가 동의해도 사람의 재미·이해도를 검증한 것은 아니다. 이는 재미 개선을 미루는 조건이 아니다. 에이전트는 근거 있는 설계 개선을 자율적으로 구현·비교하고, 사람의 반응이 미확인이라는 사실만 별도로 기록한다. 자연 플레이 참가자에게 답을 알려 준 뒤 완료했다면 도움을 받은 결과로 기록한다.

## 검증 비용과 작업 환경

- 소스·화면의 저렴한 검토로 문제를 먼저 모으고, 하나의 관련 수정 묶음에 필요한 검사를 수행한다. 문서만 바꿨다면 Unity나 APK를 다시 빌드하지 않는다. 통과한 동일 검사를 새 변경이나 의심 없이 반복하지 않는다.
- Android 동작·아트·레이아웃 수정의 인계에 개발 APK가 필요하면 저장소 스크립트로 빌드한다. 기존 APK와 companion 출력을 먼저 보관하고 새 후보는 고유 경로에 둔다. BuildAll과 버전·설정 원칙은 AGENTS.md를 따른다.
- Unity를 실행하는 작업자는 한 명만 둔다. 검토 에이전트는 읽기 전용으로 동작하고, 파일 편집 담당 범위를 겹치지 않는다. 빌드·소스 보존 대조 중에는 검사 대상 파일을 동결한다.
- 사람의 플레이 환경에 자동 입력·업데이트·재시작을 하지 않는다. 전용 QA 저장과 기기만 사용하고 실제 기기 식별자를 조작 직전에 확인한다. 계정·동의·광고 없이 검증한다.
- 작업 종료 때 완료한 수정, 남은 상위 문제, 검증한 후보와 검사하지 못한 범위만 간결하게 알린다. 작업이 끝난 뒤 저절로 계속 실행되는 것으로 표현하지 않는다. 예약 실행은 별도 요청으로 설정하고, 켜진 PC·사용 가능한 프로젝트·권한과 중복 실행 방지를 확인한다.

## 다음 게임 개선 사이클의 비교 후보

현재 사용자는 이전보다 게임을 풀어가는 재미가 생겼다고 평가했다. 그 장점을 유지하면서 아래 후보를 비교한다. 후보 등록 자체는 구현이나 재미 개선의 증거가 아니다. 다음 사이클에서 현재 버전을 확인한 뒤 가장 효과가 클 관련 묶음을 선택하며, 모두를 자동으로 구현하지 않는다.

| 후보 / 상태 | 출발 근거와 개선 가설 | 실행과 확인 |
|---|---|---|
| F01 / 재미·평가 대기 | 두 사건은 관찰·도구 사용 중심의 열 장면으로 구성돼 있다. 같은 조작 형식 안에서도 매번 새 추론을 요구하는지 확인할 필요가 있다. 현재 흐름이 지루하다고 단정하지 않는다. | 가장 반복적인 인접 장면을 행동·새 정보로 비교한다. 불필요한 관찰을 압축하거나 단서를 연결하는 실험을 개선해 전후를 비교하되, 도움 없이 필요한 정보를 얻을 수 있는 상태를 유지한다. |
| F02 / 재미·평가 대기 | 첫 사건에서 우산으로, Rain에서 편지·답장으로 이어지는 구조는 존재한다. 발견과 결말이 앞선 행동에 비례하는 성취감·여운을 주는지는 추가 설계 검토 대상이다. | 부탁 → 단서 → 변화 → 인물 반응 → 결말의 연결을 기록한다. 약한 연결이 확인되면 해당 장면의 반응·발견·결말 표현을 보강하고, 새 사건이나 분기 추가 없이 전후를 비교한다. |
| P01 / 완성도·일부 화면 확인 | Q02는 현재 완료 그림의 낙엽 식별 문제다. Q04는 이전 후보에서 기록한 상태 불일치로 최신 재현이 필요하다. 발견이 시각적으로 보이면 행동의 결과가 더 뚜렷해질 수 있다. | 현재 버전에서 재현한 항목만 대상으로 해당 물건의 중요 행동 전후와 다음 장면까지 일치시킨다. 물건의 정체성과 변화가 화면에서 보이는지 독립 검토한다. |

선택한 개선마다 `장면 / 현재 근거 / 바꿀 경험 / 변경 내용 / 전후 비교 방법 / 실제 결과 / 남은 가설`을 남긴다. 기존 사용자 반응, 에이전트 판단, 기술 검사를 구분하며 임의의 재미 점수나 완성도 백분율을 만들지 않는다.

## 다음 작업에서 사용할 짧은 지시

> Docs/QualityReview.md에 따라 현재 두 사건의 재미와 완성도를 높이는 개선 사이클을 실행해. 진행·저장 문제를 우선 확인하고, 추리·실험·전개·보상과 조작 반응·그림·소리·문장의 완성도를 각각 평가해. 상위 미해결 문제와 개선 후보를 비교해 효과가 클 변경을 스스로 선택하고 구현·검증·전후 비교·기록까지 마쳐. 정답을 아는 완주와 독립 검토를 구분하고, 실제 사람의 재미를 확인했다고 주장하지 마. 사용자 플레이 환경과 기존 파일·산출물을 보존하고, 병합·출시는 하지 마. 통상적인 구현 판단은 다시 묻지 말고 진행해.
